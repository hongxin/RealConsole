### 1. 数据层统一（session.rs）

**优点**：
```rust
// ✅ 统一的数据抽象
pub enum RoundType { Llm, Shell, System }

pub struct ConversationRound {
    pub round_type: RoundType,  // 类型字段统一

**符合原则**：

**符合原则**：

## ⚠️ 需要改进的设计

### 问题 1: 注释不完整（违反流程差异显式原则）

**位置**: `src/web/websocket.rs`

**问题描述**：
虽然函数添加了注释，但**未明确标注不同类型的处理流程差异**。

**当前代码**：
```rust
/// 执行 Shell 命令（v1.28.1: 统一回合系统）
async fn execute_shell_command(...) { ... }

/// 执行 LLM 对话（带工具调用）
async fn execute_llm_chat(...) { ... }
```

**问题**：
- 注释未说明 Shell 和 LLM 的流程差异
- 未标注 Shell 没有 `stream` 消息
- 未说明传统模式下的显示策略差异

**改进方案**：
```rust
/// 执行 Shell 命令（v1.28.1: 统一回合系统）
///
/// ## 消息流程
/// ```
/// RoundStart(type: shell) → 执行命令 → RoundComplete
/// ```
///
/// ## 与 LLM 的差异
/// - ❌ 没有 `Thinking` 消息
/// - ❌ 没有 `Stream` 消息（一次性返回）
/// - ✅ 有 `RoundStart` 和 `RoundComplete`
///
/// ## 传统模式显示
/// - 命令：`handleSubmit()` 显示（用户输入时）
/// - 输出：`round_complete` 时额外显示
async fn execute_shell_command(...) { ... }

/// 执行 LLM 对话（v1.28.1: 统一回合系统）
///
/// ## 消息流程
/// ```
/// RoundStart(type: llm) → Thinking → Stream(流式) → RoundComplete
/// ```
///
/// ## 与 Shell 的差异
/// - ✅ 有 `Thinking` 消息（显示飞轮）
/// - ✅ 有 `Stream` 消息（流式输出）
/// - ✅ 有 `RoundStart` 和 `RoundComplete`
///
/// ## 传统模式显示
/// - 命令：`handleSubmit()` 显示（用户输入时）
/// - 输出：`stream` 消息流式显示（**不需要** `round_complete` 重复显示）
async fn execute_llm_chat(...) { ... }
```

**影响**: 中等（文档质量）
**优先级**: 高（避免未来维护者重复踩坑）

### 问题 2: 魔法字符串（违反类型感知原则）

**位置**: `src/web/server.rs`

**问题描述**：
前端使用字符串字面量判断类型，而非枚举或常量。

**当前代码**：
```javascript
// ❌ 魔法字符串
if (msg.round.round_type !== 'llm' && msg.round.ai_response) {
    terminal.writeOutput(msg.round.ai_response);
}

// ❌ 魔法字符串
const configs = {
    'llm': { ... },
    'shell': { ... },
    'system': { ... }
};
```

**问题**：
- 字符串拼写错误无法在编译时发现
- 新增类型时容易遗漏某些判断
- 不符合类型驱动的设计原则

**改进方案**：
```javascript
// ✅ 使用常量
const RoundType = {
    LLM: 'llm',
    SHELL: 'shell',
    SYSTEM: 'system'
};

// 判断时使用常量
if (msg.round.round_type !== RoundType.LLM && msg.round.ai_response) {
    terminal.writeOutput(msg.round.ai_response);
}

// 配置表使用常量键
const ROUND_TYPE_CONFIGS = {
    [RoundType.LLM]: { ... },
    [RoundType.SHELL]: { ... },
    [RoundType.SYSTEM]: { ... }
};
```

**影响**: 低（功能正常，但可维护性差）
**优先级**: 中（改进代码质量）

### 问题 3: 缺少类型校验（违反类型感知原则）

**位置**: `src/web/server.rs` 的 `getRoundTypeConfig()`

**问题描述**：
配置表查询没有处理未知类型的情况，只是简单回退到默认值。

**当前代码**：
```javascript
getRoundTypeConfig(roundType) {
    const configs = {
        'llm': { ... },
        'shell': { ... },
        'system': { ... }
    };
    return configs[roundType] || configs['llm'];  // ❌ 静默失败
}
```

**问题**：
- 未知类型会静默回退到 'llm'
- 开发者无法察觉拼写错误或新增类型未配置
- 不符合"快速失败"的原则

**改进方案**：
```javascript
getRoundTypeConfig(roundType) {
    const configs = {
        [RoundType.LLM]: { ... },
        [RoundType.SHELL]: { ... },
        [RoundType.SYSTEM]: { ... }
    };

    const config = configs[roundType];
    if (!config) {
        console.error(`Unknown round type: ${roundType}, falling back to LLM`);
        return configs[RoundType.LLM];
    }
    return config;
}
```

**影响**: 低（极少情况）
**优先级**: 低（防御性编程）

### 问题 4: `Output` 消息未废弃（违反协议层完整原则）

**位置**: `src/web/session.rs` 的 `ServerMessage`

**问题描述**：
虽然现在所有交互都使用回合系统，但 `Output` 消息仍然存在且未标记废弃。

**当前代码**：
```rust
pub enum ServerMessage {
    /// 命令输出（一次性）
    Output { content: String },  // ❌ 已不再使用，但未标记

    // ...
}
```

**问题**：
- 未来开发者可能误用 `Output` 消息
- 与回合系统设计不一致
- 增加协议理解成本

**改进方案**：
```rust
pub enum ServerMessage {
    /// 命令输出（一次性）
    ///
    /// **已废弃**: v1.28.1 起，所有交互统一使用回合系统
    /// - LLM 对话：使用 `RoundStart` + `Stream` + `RoundComplete`
    /// - Shell/System：使用 `RoundStart` + `RoundComplete`
    ///
    /// 仅保留用于特殊场景（如欢迎消息）
    #[deprecated(since = "1.28.1", note = "Use RoundStart/RoundComplete instead")]
    Output { content: String },

    // ...
}
```

**或者更激进的方案**（v1.29.0 考虑）：
- 完全移除 `Output` 消息
- 欢迎消息使用新的 `SystemNotification` 消息

**影响**: 低（当前未使用）
**优先级**: 低（文档改进）

### 问题 5: 前端回合数据结构冗余（违反极简主义）

**位置**: `src/web/server.rs` 的 `createRound()`

**问题描述**：
前端维护了两份数据：服务器发来的 `round` 对象，和本地创建的 `roundData` 对象。

**当前代码**：
```javascript
createRound(round) {
    // ❌ 创建新对象，复制所有字段
    const roundData = {
        id: round.id,
        index: round.index,
        roundType: round.round_type || 'llm',
        userInput: round.user_input,
        aiResponse: round.ai_response || '',
        toolsUsed: round.tools_used || [],
        executionTime: round.execution_time || 0,
        status: this.normalizeStatus(round.status),
        timestamp: round.timestamp,
        model: round.model,
        element: null,
        expanded: true
    };

    // ... 存储 roundData
}
```

**问题**：
- 字段命名转换（snake_case → camelCase）增加复杂度
- 数据冗余
- 更新时需要同步两处

**改进方案**：
```javascript
// 方案1: 直接使用服务器数据，添加前端字段
createRound(round) {
    round.element = null;
    round.expanded = true;
    round.status = this.normalizeStatus(round.status);
    this.rounds.push(round);
    return round;
}

// 方案2: 统一命名风格（后端改为 camelCase 序列化）
// 需要修改 Rust 序列化配置
```

**影响**: 低（当前功能正常）
**优先级**: 低（代码简化）

### 问题 6: 缺少错误边界处理（违反渐进演进原则）

**位置**: `src/web/websocket.rs` 多处

**问题描述**：
错误处理使用 `?` 操作符直接传播，缺少用户友好的错误信息。

**当前代码**：
```rust
// ❌ 错误直接传播
let output = tokio::process::Command::new("sh")
    .arg("-c")
    .arg(cmd)
    .output()
    .await?;  // 如果失败，连接直接断开
```

**问题**：
- 错误信息不友好
- 连接可能意外断开
- 用户无法了解失败原因

**改进方案**：
```rust
// ✅ 友好的错误处理
match tokio::process::Command::new("sh")
    .arg("-c")
    .arg(cmd)
    .output()
    .await
{
    Ok(output) => {
        // ... 处理成功
    }
    Err(e) => {
        // 记录详细错误
        eprintln!("Shell command execution failed: {}", e);

        // 发送友好的错误回合
        if let Some(failed_round) = session.fail_round(
            &round_id,
            format!("Failed to execute command: {}", e),
        ).await {
            // 继续工作，不断开连接
        }
    }
}
```

**影响**: 中等（用户体验）
**优先级**: 中（改进错误处理）

## 💡 设计经验总结

### 经验 1: 注释是设计的一部分

**教训**: 注释不仅是"说明代码做了什么"，更应该"解释为什么这样做"和"与其他方案的差异"。

**实践**:
- 关键函数必须注释流程图
- 差异点必须显式标注
- 设计决策必须记录原因

### 经验 2: 类型系统应贯彻始终

**教训**: 后端使用类型系统，前端使用字符串，导致类型安全断层。

**实践**:
- 前端定义常量枚举
- 配置表使用常量键
- 判断使用常量比较

### 经验 3: 错误处理是用户体验的一部分

**教训**: `?` 操作符方便，但牺牲了用户体验。

**实践**:
- 关键路径使用 match 显式处理
- 错误信息应该用户友好
- 失败应该优雅降级，不应断开连接

### 经验 4: 极简主义不是删除代码

**教训**: 极简主义是"理清逻辑"，而非"减少行数"。

**实践**:
- 冗余的数据转换应该消除
- 但必要的注释和错误处理不应省略
- 简化应该在不牺牲清晰度的前提下进行
